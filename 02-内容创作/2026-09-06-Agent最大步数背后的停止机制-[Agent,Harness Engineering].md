# Agent最大步数背后的停止机制

在Agent的开发过程中，为了避免Agent一直运行，我们通常会设置一个最大步数，比如最多执行20步。

听起来很简单，加个计数器，到了上限就退出。

但如果第19步，Agent启动了几个子Agent，还在后台跑着一个测试脚本。第20步，主Agent停了，那这些任务怎么办？

如果它们还在继续运行，这个最大步数，到底限制了什么？

比如，我们让一个代码Agent修复Bug。它不断读取代码、修改文件、运行测试，测试失败之后再继续修改。

到了20步，代码改了一半，测试还没结束，系统返回一句：已达到最大步数。

限制确实生效了，但用户不知道改到了哪里，也不知道后台还有没有任务在运行。

所以，最大步数的设计，需要说清楚三件事：一步怎么算，任务怎么停，以及停止之后怎么交接。

先说第一个，一步到底怎么算？

以Claude Code为例，它是在一批工具结果准备好、即将继续下一轮时，把轮数加一。

也就是说，模型一次返回三个工具调用，这批工具执行并返回结果，在这段计数逻辑里只增加一轮，不是三轮。

而且，给主Agent配置的最大轮数，限制的是主Agent自己的执行循环。

比如主Agent启动一个子Agent分析代码，子Agent内部又执行了十轮，这十轮不会直接累加到主Agent的计数器里。

那子Agent有没有限制？

需要看它自己的配置。

Claude Code启动子Agent时，不会自动继承主Agent的最大轮数，而是使用子Agent这次运行传入的上限，或者它自身定义中的上限。如果都没配置，这条执行路径就没有这项轮数硬限制。

所以，不能认为主Agent最多20轮，子Agent也最多20轮，更不能认为所有Agent合计最多20轮。

如果我们自己设计Harness，建议主Agent和子Agent分别设置额度。如果还要控制整个任务的成本，就需要额外限制总Token、执行时间或者子Agent数量。

最大轮数控制的是循环次数，不是整个任务的总消耗。

接下来是第二个问题，达到上限，应该怎么停？

这里要区分：提醒模型停止，和从工程上阻止它继续执行。

你可以告诉模型：“只剩两步了，请尽快收尾。”

这能帮助它调整策略，但不能代替硬限制。模型仍然可能认为，再试一次就能完成。

以Claude Code为例，它的最大轮数判断分支，没有先提醒模型“快到上限了”，而是达到限制条件后退出循环，再向SDK调用方返回超限结果。

这个结果是给调用方的，不代表模型还能收到它，再额外生成一段总结。

所以，提前提醒和预留收尾预算，需要单独设计。到了硬上限，仍然由Harness，也就是模型外面的执行框架，阻止后续执行。

但是，退出主循环还不够。

因为主Agent停止决策，不代表子Agent停止调用模型，更不代表后台脚本已经退出。

如果我们定义的是“整个任务停止”，那么达到上限之后，工程系统就需要找到这个任务启动的子Agent和后台任务，并把停止请求传递下去。

对子Agent，发送取消信号；对后台脚本，调用进程终止机制。如果允许某个后台任务独立继续运行，也需要提前明确，而不是遗漏了清理。

这属于完整停止机制的设计要求，不能认为配置了Claude Code的最大轮数，就已经自动完成了整棵任务树的取消。

然后是第三个问题：后台任务停了，模型会知道吗？
这个问题之前讲过。停止后，不必为了通知再调用一次模型，但工程层需要记录最新状态，并在下一轮Query前把相关状态补进上下文，避免模型还以为任务正在运行。
关键不是让模型主动查，而是由工程层保证它继续执行时，拿到的是最新状态。

所以，最大步数不只是一个计数器。

计数器决定还能跑多少轮，取消机制决定哪些任务应该停，状态交接决定下一次能不能接着做。

把这三件事连起来，才是一套完整的Agent停止机制。
