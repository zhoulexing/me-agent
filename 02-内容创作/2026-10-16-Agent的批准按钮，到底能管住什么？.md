# Agent 的批准按钮，到底能管住什么？

最近研究 Agent 的权限时，我卡在一个很具体的问题上。

我们经常看到这些选项：只读、工作区、请求批准、完全访问，还有让 AI 帮我批准。看起来像是在选一个安全等级，但这些选项到底管什么？

比如，我不允许 Agent 用写文件工具修改文件，它能不能换一种方式，执行一段代码，把文件改掉？

顺着这个问题，我看了 Claude Code 和 DeepSeek Harness 的实现，也在自己的 agent-harness 项目里做了一套简化版本。有两个环节，需要先分清楚。

一个是审批：这次操作要不要开始，谁来决定。

另一个是沙箱：程序开始运行以后，能访问哪些资源，哪些操作会被系统拦住。

为什么要拆开看？我们拿 Bash 举个例子。Bash 就是 Agent 用来执行命令的工具。

同样调用这个工具，执行 `cat a.txt`，通常是在读取文件。后面加上 `> b.txt`，就会把内容写进另一个文件。再换成 `node job.js`，执行的是一整个程序，里面可能读文件、写文件，也可能访问网络。

所以，仅凭工具名字，没办法判断这次调用会做什么。

简单工具可以由开发者声明它的权限类型，比如读文件、写文件。Bash 这样的通用执行工具，还需要结合具体参数判断。遇到任意脚本时，也不能因为命令里没出现“写入”，就认定它只读。

这里用一小段动画，把整个过程拆开看。

> **【插入解说视频：约 60—70 秒，以下为旁白】**
>
> 假设 Agent 要写一个脚本，再执行它。我们把沙箱设置成：允许写工作区，禁止写工作区外。
>
> 第一步，模型请求写入 `job.js`。框架检查这次调用，按策略请求批准。批准后，文件才写入工作区。到这里，脚本还没有运行。
>
> 第二步，模型请求执行 `node job.js`。这是一次新的工具调用，要重新经过权限检查。我们批准它在当前沙箱里运行。
>
> 脚本先写工作区里的结果文件，成功了。接着，它尝试写工作区外的文件，这次被操作系统拦住。
>
> 同样的写入，如果通过一个没有沙箱限制的命令执行入口运行，就可能成功。只拦住写文件工具，管不住所有写入路径。
>
> 批准决定这次调用能否开始；沙箱继续约束执行范围。而且，后一次写入失败，不会自动撤销前一次已经写好的文件。

**【切回口播】**

那实际产品是怎么做的？

Claude Code 的 Bash 工具有专门的权限检查函数。它会分析具体命令，检查允许、拒绝和询问规则，也会处理子命令、重定向和一些已知的只读命令。

比如，前半句是读文件，后半句是执行脚本，就不能因为前半句允许了，把整条命令都放过去。

但这类分析也有边界。一个脚本还能加载别的文件、启动别的程序，不能指望看一眼命令，就证明它后续所有行为都安全。Claude Code 也有沙箱机制；开启沙箱自动允许后，一些操作可以因为受边界限制而直接执行，包括边界内的写入。

DeepSeek Harness 则把这些能力拆成了插件。它的官方默认组合，给 Bash 配了沙箱：先在当前范围内执行，如果需要更大的范围，再请求批准。这里并不需要把每个脚本预先完整分析一遍。

它还有一个可选的 Auto review 插件。执行前，再调用一次模型，结合工具参数和授权上下文，判断这个动作能不能放行。当前官方版本中，没有通过模型审查的动作，还可能转给用户批准。

这里有个容易忽略的细节：DeepSeek 这个 Auto 模式，获准后是以完全访问的范围执行。所以，“有 AI 帮我审核”和“有沙箱限制”，也要分开看。

回头再看最开始那些模式名，就容易理解了。

“只读”和“工作区”，主要描述访问范围。“请求批准”和“帮我批准”，主要描述谁来决定是否执行。产品会把它们组合起来，但不同产品，同一个名称，具体规则可能不一样。

这次研究让我更想在做 Agent 时检查三件事：执行前，谁决定放行；执行后，谁限制范围；换一种工具、换一种语言、再启动一个子进程，这些限制还在不在。

尤其是第三件。我们希望 Agent 越来越会解决问题，它也就越来越有能力找到其他执行路径。权限设计需要覆盖这些路径，才能让我们知道，自己到底给它放了多大的权。

## 来源与事实边界（不口播）

1. [Claude Code 权限文档](https://code.claude.com/docs/en/permissions)：Bash 规则、复合命令、重定向与只读命令。源码研究使用本地研究快照，不宣称它等于当前官方发行版源码。
2. [Claude Code 沙箱文档](https://code.claude.com/docs/en/sandboxing)：审批与沙箱是不同控制；沙箱自动允许也可放行边界内写入，仍受具体规则和模式影响。
3. [DeepSeek 官方基础插件组合](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/base/cordis.patch.yml)：默认工作区写入与 ask 策略；ask 不表示每条 Bash 都询问。
4. [DeepSeek Bash 插件](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/shell/tool-bash/README.md)：通过执行器实施沙箱，扩大范围时请求审批。
5. [DeepSeek Auto review 说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/experimental/auto-review/README.md)与[权限预设源码](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/interaction/permission-presets/src/index.ts)：2026-10-16 已在线核对，当前 Auto 使用 danger-full-access + ask；reviewer 拒绝后能否转人工还取决于审批策略及后续门禁。委派的进程内子 Agent 可固定为 never；技术失败不执行。本地 2026-09-23 快照仍是旧的直接拒绝分支，正文采用本轮在线核对结果。
6. 网络、凭证、外部 API 权限是额外维度。正文和动画以本地文件写入为例；文件只读不能推导为没有网络或外部副作用。没有沙箱时“可能成功”仍取决于操作系统账户权限等实际条件。
7. 提示词要求模型先申请批准，不等于宿主强制拦截。教学代码的批准不会扩大沙箱；DeepSeek 的沙箱升级审批是另一种明确请求更宽范围的机制。
