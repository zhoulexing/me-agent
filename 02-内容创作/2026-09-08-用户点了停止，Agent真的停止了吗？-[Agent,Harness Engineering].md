# 用户点了停止，Agent真的停止了吗？

你让Agent生成一段视频，同时准备发布文案。执行到一半，发现需求说错了，于是点击停止。

界面不再输出，你以为任务已经结束。但后台子Agent可能还在写文案，视频服务也还在生成，甚至继续计费。

那刚才这个停止按钮，到底停了什么？

对于Agent开发工程师来说，需要说清楚三个问题：停止信号怎么传到子任务，请求已经发到外部还能不能取消，以及取消和成功同时发生时，最终状态怎么算。

先说第一个，停止信号怎么传下去？

很多人实现停止功能，首先想到的是取消模型请求。

这一步有用，但它只处理了执行链路中的一个环节。模型不再生成，不代表已经启动的工具、子Agent和后台进程也停止了。

一种常见机制，是给当前执行创建一个取消控制器，比如JavaScript里的AbortController。

主Agent把它的signal传给子任务。用户点击停止，就调用abort，通知这些任务停止。

但要注意，AbortController只是一个通知机制，不是强制终止开关。

子任务需要检查信号，停止后续循环；正在执行的网络请求，需要支持取消；本地进程，则需要调用进程终止方法。

如果某段代码没有处理取消信号，它仍然可能继续执行。

这里还要区分同步和异步子任务。

同步子任务可以共享父级的取消信号。父级发出取消，子任务就能感知到。

但异步子任务往往有自己的生命周期和取消控制器，不能指望主Agent停止时，它也自然停止。

以Claude Code为例，同步子Agent默认共享父级控制器，异步子Agent则使用独立控制器。后台Bash转入后台后，也会移除原来的取消监听，需要通过任务管理器找到进程，再显式停止。

所以，如果你的停止按钮表示“停止整个任务”，就需要先禁止继续派发新工作，再找到这次执行所属的同步子任务、异步子Agent和后台进程，分别传递取消。

不能只把主Agent的循环停掉，就认为整件事结束了。

接下来是第二个问题，请求已经发到外部系统，还能取消吗？

比如视频生成任务已经提交给外部服务，这时取消本地HTTP请求，只能说明本地不再等待响应，不能证明服务端停止生成。

能不能取消，要看外部服务提供什么能力。

如果支持取消，就用外部任务ID调用取消接口，再确认最终状态。是取消成功、取消失败，还是任务已经完成，都要以外部系统确认的结果为准，不能把“取消请求已接收”当成“已经取消”。

无论外部任务能否取消，本地都应该停止后续任务，给用户的反馈也要准确。

比如：“已停止后续处理，但视频服务不支持取消，当前生成可能继续，结果不会自动发布。”

然后是第三个问题：用户点击取消的同时，任务恰好成功，最终状态怎么判？

核心是把取消意图和执行结果分开。

用户点击停止，先记录取消请求；执行者确认取消，才标记“已取消”。如果最终确认任务已经成功，就保留成功，同时记录用户曾请求取消；暂时无法确认，就保持待核验。

这些状态由工程层统一更新，避免成功和取消的回调互相覆盖。有冲突时，再查询外部系统确认。

比如视频恰好生成完成，可以反馈：“已停止后续处理。视频已经生成，结果已保留，未继续发布。”

**任务成功，不代表可以继续执行用户已经叫停的后续操作。**

最后，这些停止结果，要不要让模型知道？

要区分反馈用户和同步模型：用户点击停止后，工程层可以直接显示取消进度和结果，不需要专门调用一次模型生成“已停止”。

但模型后续继续处理相关任务时，需要知道最新状态，否则可能还以为视频正在生成，继续等待，甚至重新启动一份。

所以，无论最终是取消成功、取消失败，还是任务已经完成，都应该记录真实结果，并在后续继续处理前同步给模型，而不必为此立即唤醒已停止的Agent。

最终，一个停止按钮需要交代清楚三件事：**哪些已经停止，哪些无法阻止，以及停止之前，哪些事情已经发生。**
