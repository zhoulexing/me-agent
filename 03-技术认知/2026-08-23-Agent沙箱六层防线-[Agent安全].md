# Agent 沙箱六层防线：从物理隔离到系统提示词

现在的 Agent，已经不只是坐在那里陪我们聊天了。它可以读文件、写代码、执行命令，还能拿着账号和密码调用外部系统。

问题也随之而来：如果 Agent 理解错了我们的意思，或者网页里藏着一段恶意提示，诱导它删除文件、上传数据，我们靠什么拦住它？

很多人的第一反应是给它加一个沙箱。但“沙箱”不是某一种具体产品，而是一层一层的防线。最下面是物理机器，中间有虚拟机、容器和进程沙箱，最上面还有 Hook 和系统提示词。它们做的事情完全不同，隔离的程度也会不一样。

我们先从一台真实服务器开始。服务器有 CPU、内存、磁盘和网卡，但程序通常不能直接操作这些硬件。中间有一个总管家，叫操作系统内核，也就是 Kernel。

程序想打开文件、创建进程或者连接网络，都要向内核提出请求，这种请求叫系统调用。比如 Agent 想读取一个文件，会调用 `open()`。真正判断文件能不能打开的，是内核。

所以理解沙箱有一个很重要的抓手：程序想做一件事时，最后是谁在批准？

最直接的隔离，是让两个 Agent 跑在两台物理服务器上。两边的 CPU、内存、磁盘和内核都不共享。这种边界很硬，但成本也高。我们不可能每启动一个 Agent，就准备一台新服务器。那我们能不能在一台物理服务器中虚拟出多台计算机，这就是虚拟机。

理解虚拟机，要先说清楚两个经常一起出现的词：KVM 和 VMM。

比如Linux, KVM 是内核中的虚拟化模块。就是替 Linux 打开并管理这套模式，让虚拟机能够借用真实 CPU 运行，同时又和宿主机保持隔离。

但只有 CPU 和内存还不够，一台计算机还需要磁盘、网卡和启动设备。负责把这些东西组织起来的用户态程序，就叫 VMM，也就是虚拟机监视器。

可以把 KVM 想成虚拟机的发动机：它解决“虚拟机里的代码怎样在真实 CPU 上运行”。VMM 更像整车厂：它把发动机、磁盘、网卡和启动流程组装成一台能用的虚拟电脑。

虚拟机最关键的地方，是它拥有自己的 Guest Kernel，也就是客户机内核。虚拟机里的 Agent 调用 `open()` 时，首先面对的是 Guest Kernel，而不是宿主机的 Host Kernel。即使虚拟机内部被攻破，攻击者还要继续突破虚拟机边界，才能接触宿主机。

聊完虚拟机，继续聊，容器。普通容器没有自己的内核。容器里的进程最终共享同一个 Host Kernel。它之所以看起来像一个独立环境，主要依靠两个 Linux 机制。

第一个叫 Namespace，也就是命名空间。它隔离的是进程看到的世界，让不同容器看到不同的进程编号、网络设备和文件挂载。第二个叫 Cgroups，也就是控制组。它负责限制一个容器最多可以使用多少 CPU、内存和磁盘 IO。

一句话记住：Namespace 隔离视图，Cgroups 限制资源。

/proc 就能很直观地体现这种视图隔离。它看起来像一个普通目录，但里面的信息并没有真正保存在磁盘上。它属于虚拟文件系统，更像是内核提供的一块实时信息看板。当程序读取 /proc 里的文件时，内核才会动态返回当前的进程、CPU 和内存状态。

Namespace 和 Cgroups 是容器隔离的基础，但容器具体怎么运行，还有不同的方案。

最常见的是 runc。它直接使用宿主机内核提供的 Namespace 和 Cgroups，所以容器仍然共享 Host Kernel。

gVisor 则在容器和 Host Kernel 之间增加了一个用户态的 Sentry。容器发出的很多 Linux 系统调用，会先由 Sentry 接管和处理，从而减少容器直接接触 Host Kernel 的机会。

Kata Containers 更进一步。它会把容器放进一个轻量虚拟机，让容器使用独立的 Guest Kernel，从而获得更接近虚拟机的隔离边界。

企业里经常使用的 Kubernetes，并不是另一种底层隔离技术，而是管理和调度容器的平台。Pod 是 Kubernetes 的最小调度单位，负责把一组需要共同运行的容器放到某台机器上。至于 Pod 底层使用 runc、gVisor 还是 Kata，则取决于配置的容器运行时。

不过，把 Agent 隔离在 Pod 里还不够。Pod 解决的是不同工作负载之间的边界，但 Pod 内部仍然可能存在配置文件、业务代码和访问凭证。如果我们还希望在同一个 Pod 内，对不同 Agent 或不同任务进行更细粒度的文件隔离，比如某个 Agent 只能访问自己的工作目录、只能读取指定配置，不能查看其他任务的文件和敏感凭证，那么仅靠 Pod 的隔离就很难满足。

所以，还需要在 Pod 里面增加一层进程级沙箱，主要解决文件和网络两个问题。

文件方面，可以用 bubblewrap 给 Agent 创建一个独立的文件视图：大部分目录只读，只开放自己的工作目录写入。这样即使执行删除操作，影响也会被限制在自己的目录里。还可以配合 seccomp，过滤部分危险的系统调用。

网络方面，先禁止 Agent 直接访问外网，只允许它通过代理发送请求。代理会检查目标域名和访问规则，再决定是否放行。

真实凭证也放在 Agent 进程之外。Agent 只能拿到一个占位符，请求经过代理并发往指定服务时，代理才会换成真实凭证。

在进程沙箱之上，还可以再加一层 Hook，即 Agent 框架里的工具调用拦截器。模型准备执行命令如 Bash 时，Hook 会先检查命令、路径和风险，再决定允许、拒绝，还是让人确认。

Hook 由程序代码执行，比提示词更确定，但它只能拦住经过这个入口的操作。没有接入 Hook 的工具，或者已经启动的进程，不一定会再次经过检查。

再往上一层是系统提示词。我们可以告诉模型：不要读取工作目录以外的文件，删除数据前必须确认，也不要把用户信息发送给第三方。

提示词能理解复杂的业务语义，但不是硬安全边界。模型可能理解错误，也可能受到 Prompt Injection。它更像一份员工手册：告诉 Agent 应该怎么做；而 Hook 和进程沙箱，才是真正限制它能够做什么。

其实除了系统提示词之外，还可以再用户输入问题进来之前再加一层安全模型的检测，包括输出也是一样的，核心是结局系统提示词的注入攻击。

最后，把这些层放在一起，就能看懂真正的纵深防御。

提示词先告诉 Agent 不要删除敏感文件；如果模型仍然发起删除，Hook 可以把调用拦下来；如果 Hook 漏掉了，进程沙箱还能拒绝写入；如果进程沙箱被绕过，容器继续限制它能接触的节点资源；如果容器逃逸，虚拟机和物理隔离继续控制最终的影响范围。

越靠近底层，约束越硬；越靠近模型，理解越强。但理解不能代替权限控制，任何一层也不应该被绝对信任。

所以，看一个 Agent 沙箱，不要只看产品和技术名词，而要看三件事：保护什么？谁来强制？失效之后谁来兜底？

这才是判断 Agent 沙箱的关键。
