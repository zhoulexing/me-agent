# Agent后台任务该怎么设计

在Agent开发过程中，像生图、生成视频这类工具，往往需要执行很长时间。

比如用户要生成一段产品视频，同时准备发布文案。视频需要几分钟，文案却可以先写，没必要一直等着。

所以，我们需要设计一个可以后台运行的能力，比如先返回一个任务ID，让Agent继续准备文案。

但返回ID之后，谁负责管理这个任务？让模型不断调用工具查询进度吗？成功、失败，或者用户中途取消，又该怎么反馈？

一个完整的后台任务能力，需要解决三件事：谁接管、谁等待、怎么反馈。

## 先说第一个，谁来接管这个任务？

工具调用已经返回，但视频可能还在生成。这时候，工程系统需要知道：任务属于哪个会话、当前是什么状态、结果在哪里，以及怎么取消。

这些信息和操作，应该由后台任务管理器统一维护。

所以，返回任务 ID 不只是告诉模型“任务启动了”，也意味着这个任务已经被系统接管。后续查询状态、获取结果、取消任务，都围绕这个任务 ID 进行。

更重要的是，任务管理器需要保证幂等。

Agent 在执行过程中可能因为超时、网络异常或重试机制，重复发起同一个任务。如果每次请求都重新创建任务，就可能生成多个视频、重复执行脚本，甚至产生额外成本。

因此，同一个任务需要有稳定的身份标识。重复请求到来时，系统应该识别它已经存在，直接返回原来的任务和状态，而不是重新执行一次。

至于任务具体在哪里执行，则由任务类型决定：脚本可以通过子进程运行，子 Agent 可以在当前服务中启动独立异步任务，视频生成也可以交给外部服务，本地只保存对应的任务 ID。

任务管理器负责统一管理任务生命周期，并保证同一个任务不会因为重复请求而被重复执行。

## 第二个问题，谁来等待？

一种最直接的做法，是让模型隔一会儿调用一次查询工具。

查一次，正在生成；再查一次，还是正在生成。没有获得多少新信息，却不断消耗 Token 和执行轮数。

所以，模型只需要判断接下来是否依赖这个结果，真正的等待应该交给工程层。

比如视频还在生成，但文案还没写，可以先异步生成视频，Agent 继续写文案。文案写完后，如果视频还没生成，Agent 也可以继续处理其他事情。

等视频真正生成完成后，由工程层主动通知模型，而不是让模型不断查询任务状态。

核心原则就是：模型负责决策，工程层负责等待；任务完成后，再通知模型继续执行。

## 第三个问题，结束或者中断后，怎么反馈？

先看正常结束。

任务无论成功还是失败，都应该先更新状态、保存结果，再产生一条完成事件。

如果 Agent 正在执行其他事情，这条事件先进入消息队列，在合适的执行边界加入上下文；如果 Agent 已经空闲，再按策略触发下一轮执行。

这里要避免两个问题。

第一，不要因为一个后台任务完成，就给正在运行的同一个 Agent 再并发启动一轮执行。

第二，要避免重复消费。如果 Agent 已经通过等待工具拿到了结果，完成事件就不应该再次触发处理，否则同一个结果可能被分析两遍，甚至向用户回复两次。

再看中断。

用户说“不做了”，要区分是不再等待，还是要真正取消后台任务。

停止等待，任务可以继续执行；取消任务，则需要任务管理器找到对应的执行者，并真正发出停止请求。

本地脚本可以终止进程，外部服务则需要调用取消接口。但“发出取消请求”不等于“任务已经停止”，所以状态上要区分“取消中”和“已取消”。

如果无法取消，或者暂时无法确认是否已经停止，就应该如实反馈。

任务最终的状态和结果都要保留。后续 Agent 再处理这个任务时，应该先读取最新状态，而不是沿用之前的判断。

## 最后总结一下

作为Agent开发工程师，设计后台能力时，可以按任务的生命周期检查：

启动时，有没有完成任务登记、归属和并发控制？

执行中，有没有查询和等待能力，能不能避免模型反复轮询？

结束时，成功或失败能不能交给正确的Agent，通知会不会遗漏或者重复处理？

中断时，能不能把取消传到实际执行者，并反馈真实状态？

如果还要求服务重启后继续管理任务，就需要进一步考虑持久化和恢复。仅仅把输出日志保存到文件，不代表任务本身就能恢复。
