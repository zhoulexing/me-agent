# Peter Steinberger：成长经历与 Builder 路径

- **研究日期**：2026-07-13
- **系列进度**：第 2 天 / 共 8 天
- **今日主题**：成长经历与 Builder 路径
- **阅读时长**：约 10–15 分钟

## Executive Summary｜核心摘要

Peter Steinberger 今天表现出的 Agentic Engineering 能力，并不是 2025 年突然由模型赋予的。更准确的解释是：他先在 PSPDFKit 的十三年里形成了识别真实问题、设计开发者产品、维护跨平台系统、管理远程团队和接受他人实现差异的能力，随后 Coding Agent 把这些能力放大了。[1][2][4][6]

PSPDFKit 的起点很小：一个朋友需要在 iPad 上可靠地展示 PDF，而当时的方案不够好。Peter 没有先论证“文档基础设施市场”，而是从一个具体体验出发，做出能够直接嵌入其他 App 的 iOS SDK。产品在早期便实现自我供养，随后从单人项目扩展到多平台、分布式团队和企业级文档基础设施。[3][4][6][13]

这条路径中最重要的转折不是 2021 年超过 1 亿欧元的战略投资，而是 2014 年前后 Peter 对自己的角色做出的选择：继续做一个规模有限的 iOS 产品，还是建立一家真正的多平台公司。选择后者意味着他必须减少亲自编码，学习招聘、授权、商业、客户和组织管理。[6][7] 这种转变最终导致了压力和倦怠，却也训练了他后来管理 Agent 所需的核心能力：允许实现与自己想象不同，只守住架构、结果和关键约束。[1][2]

**今天的核心判断是：OpenClaw 不是 Peter 的第二次“从零开始”，而是 PSPDFKit 训练出的产品判断、系统设计和授权能力，在新的 Agent 工具链上重新组合。** AI 让他重新成为高产的一线 Builder，但真正决定他能构建什么的，仍是此前十三年形成的问题意识和工程品味。

## Introduction｜研究问题：一个 AI Builder 是怎样形成的

履历式介绍通常会把 Peter 的路径压缩成几句话：奥地利 iOS 开发者，创办 PSPDFKit，获得成功后退出，几年后用 AI 做出 OpenClaw。这种叙述解释了“发生了什么”，却没有解释“能力如何形成”。

今天更关心四个问题：

1. 他如何从一个局部技术问题识别出可持续产品？
2. PSPDFKit 从单人项目变成全球开发者工具公司时，他被迫学会了什么？
3. 为什么成功退出之后，他反而一度失去构建能力？
4. Coding Agent 为什么能让他恢复，而不是仅仅让他写代码更快？

这四个问题共同指向一个结论：Builder 不是“会做东西的人”这么简单。成熟 Builder 同时拥有问题选择、产品取舍、技术判断、反馈设计和资源组织能力。Coding Agent 可以极大放大这些能力，却不能凭空替代它们。

## Main Analysis｜一、从 iOS 工程师到单人产品

### 1. 起点不是创业愿景，而是一个令人不满意的体验

Peter 的专业起点是 Apple 开发生态。他长期从事 iOS 开发，后来才逐渐从工程师转成 CEO。[6] PSPDFKit 官方历史把项目起点描述为：2011 年，为了把一本杂志带到 iPhone，需要一个可靠的 PDF Viewer。[3] Peter 在 2026 年的 Lex Fridman 访谈中给出的版本更生活化：他想帮助朋友在 iPad 上展示 PDF，试过现有方案后觉得体验不好，于是产生了“我能做得更好”的判断。[1]

这个起点体现了 Peter 之后反复出现的产品模式：

- 问题首先发生在自己或身边人的真实使用中；
- 市面并非完全没有解决方案，只是现有体验不够好；
- 他愿意进入一个表面普通、实际充满细节的领域；
- 第一目标不是写商业计划，而是做出自己愿意使用的版本。

OpenClaw 十五年后的起点几乎相同。Peter 想要真正存在于个人设备和消息渠道中的 Agent，等待了一段时间，发现大厂没有交付自己想要的产品，于是把 WhatsApp 与 Coding Agent CLI 接起来。两次创业表面上分别是 PDF 和 AI，底层动作却都是：“为什么这东西还不存在？那我先做一个。”[1][15]

### 2. PSPDFKit 选择的是“嵌入式能力”，而不是终端 App

PSPDFKit 不是一个普通 PDF 阅读器，而是嵌入其他产品的 SDK。Peter 在 2019 年的访谈中用 Dropbox 和航空公司驾驶舱举例：用户在这些 App 内看到的文档界面、搜索和文字选择等能力，可以由 PSPDFKit 提供。[6]

这个产品形态对 Builder 的训练非常特殊。终端 App 可以通过 UI 更新引导用户适应变化，SDK 却要进入成千上万个外部代码库。API 一旦发布就很难随意修改；跨平台功能既要遵循 iOS、Android、Web 各自的开发习惯，又要维持整体一致性。PSPDFKit 的工程文章明确说明，团队需要保守地演进公共 API，并通过 Proposal 在实现前定义各平台接口；许多底层能力先进入共享的 C++ Core。[4]

这意味着 Peter 很早就被迫学习一种超越“功能能跑”的工程标准：

- API 是否能长期稳定；
- 未来扩展是否会破坏已有客户；
- 抽象是否适用于不同平台；
- 文档和示例是否能让陌生开发者自行集成；
- 一个局部设计会不会成为未来数年的兼容负担。

这正是 Agent 时代仍然稀缺的能力。模型可以迅速生成实现，但公共接口、系统边界和长期兼容仍需要人承担判断责任。

## Main Analysis｜二、从单人产品到多平台公司

### 1. 早期成功来自聚焦与自我供养

PSPDFKit 在 2011 年前后从单人项目开始。Peter 在 2019 年访谈中称，产品发布几个月后便能够在财务上自我维持，之后长期依靠自身收入发展。[6] 这种 Bootstrapped 路径让公司在早期可以把注意力放在产品、开发者体验和客户需求上，而不是融资节奏。

但早期成功也带来一个陷阱：一个人在单一平台上可以保持极高控制力，却很难扩展成跨平台基础设施。2011 至 2013 年，PSPDFKit 主要只有 iOS 版本；Android 后来需要独立 UI，以及新的 PDF 解析与渲染 Core。[13]

### 2. 2014 年的关键选择：保持“小而美”，还是成为真正的公司

Peter 在 Semaphore 访谈中把 2014 年视为重要转折。当时他必须决定：继续做规模有限的 iOS 产品，主要满足自己写代码和获得收入的愿望；还是承认移动世界已经不可能只关注 iOS，扩展到 Android、Web 和其他平台，把项目变成严肃的公司。[6]

他选择了后者，并开始引入财务、业务、后端和管理方面的人才。这可以看作 PSPDFKit 的“2.0”：产品不再等于 Peter 自己写出的代码，而是一套由不同团队、平台和流程共同维护的系统。[6]

到 2019 年，PSPDFKit 已从单人项目成长为 40 多人的分布式公司，并覆盖 iOS、Android、Web、Windows 和 macOS。[4][6] 后续访谈提到团队规模继续超过 70 人。[2]

### 3. 远程公司训练的是显式协作

PSPDFKit 很早就是分布式团队。公司总结的远程文化关键词是信任、灵活、纪律和团队连接。[5] 对 Peter 来说，这意味着大量隐性知识必须显式化：技术方案要写成 Proposal，API 决策需要跨平台讨论，团队不能依赖随时走到某个人桌边解决问题。[4][5]

这和 Agent Harness 有直接联系。Agent 与人类远程同事当然不是一回事，但二者都要求：

- 工作目标不能只存在于负责人脑中；
- 代码库要能被不了解全部历史的执行者导航；
- 决策要有可查阅的文档；
- 结果要通过自动化验证，而不是依赖作者口头保证；
- 授权必须与明确边界同时存在。

Peter 今天强调的项目文档、`AGENTS.md`、CLI、测试闭环和原子提交，并非完全由 AI 催生。它们可以被理解为分布式软件组织经验的机器化延伸。[10][11]

## Main Analysis｜三、从亲自实现到通过他人交付

### 1. 管理团队迫使他放弃实现层面的完美主义

Peter 早期最感兴趣的是继续写代码，但随着公司扩大，他逐渐变成 CEO，做更多业务和更少编码。[6] Pragmatic Engineer 对他的访谈总结了一个很有解释力的观察：管理 70 多人的开发团队，迫使他接受代码不会总是完全符合个人偏好；这种放弃实现层完美主义的能力，后来让他更善于使用 Coding Agent。[2]

这并不表示他不在乎质量，而是质量控制层次发生了变化。单人开发者可以通过逐行阅读保证“这是我会写出的代码”；组织负责人必须通过架构、接口、测试、评审和责任边界保证“这段由别人写出的代码满足系统需要”。

从这个角度看，Peter 后来“不读大部分代码”的工作流不是突然抛弃工程纪律，而是把公司管理期间形成的授权方式迁移给 Agent：

- 人确定问题与架构；
- 执行者完成实现；
- 自动化测试和真实使用提供反馈；
- 出现偏差时，人修改方向而不是接管每一行代码。

### 2. 但角色转变也逐渐耗尽了他

授权能力的获得伴随着明显成本。Peter 在 Lex 访谈中说，自己经营 PSPDFKit 十三年，长期处于高压状态；真正使他倦怠的主要不是编码量，而是联合创始人分歧、人员问题、客户压力和必须处理所有无法向下解决的事务。[1]

这揭示了 Builder 与 CEO 角色之间的张力。Builder 从制作和反馈中获得能量，CEO 的工作则越来越多地变成组织冲突、资源配置和风险承担。公司越成功，创始人越可能远离最初令自己投入的活动。

在离开前，Peter 花了约两年让自己在组织中变得不再不可替代。2021 年，Insight Partners 对 PSPDFKit 进行超过 1 亿欧元的首次战略投资；公开报道同时指出 Peter 与 Martin Schürrer 退出全职岗位，但仍保留重要权益。[7][8]

需要严格区分：超过 1 亿欧元是公司获得的战略投资规模，不等同于 Peter 个人拿到的金额。Peter 本人的介绍将这段经历概括为九位数退出，但具体个人交易结构并未完整公开。[12]

## Main Analysis｜四、成功之后的空洞与重新成为 Builder

### 1. 离开公司不等于立即获得自由

Peter 在 2025 年的个人文章中描述，出售股份并离开经营十三年的 PSPDFKit 后，他感到自己连同公司身份一起被掏空。他尝试旅行、搬到新的国家、治疗和各种生活体验，但没有迅速找到新的目标。[9]

在 Lex 访谈中，他给出的描述更直接：离开前长期压力已经耗尽了“写出代码”的能力；退出后，他一度面对屏幕却无法构建，于是离开原有生活，试图补回此前错过的部分。[1]

这段经历说明，Builder 身份不仅是一组技能，也是一套意义来源。长期把自我与公司绑定之后，即使经济问题已经解决，失去需要解决的难题仍会造成明显空洞。

### 2. 回归不是因为发现 AI 商业机会，而是重新获得构建反馈

2024 年末到 2025 年，Peter 逐渐重新开始制作小工具。他在《Finding My Spark Again》中写道，真正让自己恢复的，是再次把想法变成东西；AI 的快速进展让这种创造过程重新变得令人兴奋。[9]

他的回归过程不是直接决定“我要创办一家 Agent 公司”，而是连续试做：终端工具、Mac 自动化、VibeTunnel、浏览器能力、消息数据实验、各种 CLI，最后才出现 OpenClaw。[1][10][14][15]

这条顺序非常重要：

1. 先重新开始玩和构建；
2. 在大量小项目中学习模型能力边界；
3. 为自己制作可组合的 CLI 和自动化；
4. 发现个人 Agent 可以调用这些已有工具；
5. 将多个实验连接为可持续使用的产品；
6. 在真实使用和社区反馈中快速演化。

因此，OpenClaw 的“一小时原型”容易产生误导。连接 WhatsApp 与 Coding Agent 的最初代码可能只花了一小时，但它背后有十三年开发者产品经验、数月 Agent 实验，以及一整套此前制作的工具。原型很快，形成判断并不快。[1][15]

## Synthesis｜五、Peter 的 Builder 能力究竟来自哪里

### 能力一：从自己的不满中发现普遍问题

PSPDFKit 与 OpenClaw 都不是从市场报告开始，而是从 Peter 自己无法接受的体验开始：PDF 在 iPad 上表现不好；理想中的个人 Agent 一直没有出现。[1][3][15]

但“为自己构建”并不天然意味着有市场。Peter 的关键能力是识别哪些个人不满代表更普遍的需求，并把私人解决方案抽象成他人可使用的平台。

### 能力二：把体验问题追到底层系统

普通 Builder 可能做一个更好看的 PDF 阅读器，Peter 做的是可嵌入其他 App 的跨平台 SDK；普通 AI 用户可能写一组提示词，他做的是连接消息、会话、工具、设备和工作区的 Agent Runtime。

这说明他的习惯不是停留在界面修补，而是向下寻找可以重复利用的基础能力。

### 能力三：理解“接口比实现活得更久”

PSPDFKit 的客户把 SDK 集成到自己的产品中，因此 API 稳定性、跨平台一致性和未来扩展成为长期责任。[4] 这种训练让 Peter 更自然地关注系统边界、工具契约、CLI 和组件关系，而不是只关注当前实现是否漂亮。

### 能力四：通过授权扩大产能

从单人开发者变成 70 多人公司的负责人，迫使他接受别人用不同方式完成实现，并把质量控制上移到架构、流程和结果。[2] Coding Agent 到来后，这种能力成为巨大杠杆：很多工程师需要先学习“如何不亲自控制每一行”，Peter 已经在公司管理中完成了这次转换。

### 能力五：保持高频、低成本的产品反馈

Peter 的回归不是靠宏大规划，而是靠不断做小工具、亲自使用和快速修正。他的工作流强调 CLI 优先、真实 Dogfooding、出现问题立即调整。[10][11] 这使 AI 的速度不只是产生更多代码，而是缩短“想法—可用产品—体验反馈—下一次判断”的周期。

## Limitations｜局限与反方解释

第一，Peter 的人生叙事主要来自本人长篇访谈和博客。它们适合理解动机，却可能把复杂的公司历史压缩成更连贯的个人故事。PSPDFKit 的成功显然也依赖联合创始人、员工、客户和合作伙伴，不能被简化为单一英雄叙事。

第二，公开资料对公司创办年份存在 2010 与 2011 的差异。Peter 在 2019 年采访中说自己于 2010 年开始，Nutrient 官方则使用 2011 年作为成立年份。[3][6] 更合理的理解是产品早期开发与公司正式形成存在时间差，而不是强行选定一个唯一日期。

第三，“管理团队训练了管理 Agent 的能力”是有证据支持的解释，但仍属于综合推论。人与 Agent 在责任、动机、沟通和错误模式上差异很大，不能把团队管理方法机械迁移给模型。

第四，Peter 当前的高产建立在丰富经验、资金自由、个人项目形态和较高模型成本之上。它不能证明所有开发者都应采用相同的并行度、主分支策略或代码审查方式。

## Recommendations｜对你的具体启发

### 1. 先寻找“持续让自己不满”的真实问题

PSPDFKit 与 OpenClaw 都来自长期存在的真实不满。对于你自己的 Agent 项目，比追逐新的框架更重要的是记录：哪些任务你每周重复、哪些交互总让你觉得低效、哪些信息明明存在却无法被系统调用。

### 2. 把一次性解决方案抽象为稳定能力

Peter 的路径不是只解决一次 PDF 展示，也不是只完成一次 WhatsApp 问答。他会继续追问：能否成为 SDK、CLI、Skill、Gateway 或可复用工具？你的 Skills 和本地资料目录也可以采用同样判断：重复三次以上且边界相对稳定的操作，值得收敛成固定入口。

### 3. 把“允许别人实现”作为使用 Agent 的前置能力

如果你要求 Agent 生成的每一行都与自己亲手编写完全相同，Agent 很难形成真正杠杆。更有效的做法是明确不可妥协的部分：接口、数据边界、验证方式、安全要求和用户体验；其余实现允许存在差异。

### 4. 不要把一小时原型误认为一小时能力

OpenClaw 的初始连接很快，但背后有多年积累。看到别人的高速产出时，更值得研究的是他提前准备了哪些工具、文档、判断框架和反馈系统，而不是只模仿最终提示词。
