# Peter Steinberger：从 X 到博客，他公开表达的 AI 世界观

- **日期**：2026-07-17（Asia/Shanghai）
- **研究阶段**：首期第 6 天
- **今日主题**：X、个人博客及其他平台公开观点
- **阅读时长**：约 10–15 分钟

## Executive Summary｜今日主题与核心判断

Peter Steinberger 的公开表达，不适合整理成一套固定不变的“AI 理论”。更准确的读法是：**把他的 X、博客、开源仓库和社区活动看成一份高速更新的 Builder 实验日志。** X 记录刚刚发生的判断，博客补上过程、语境和自我修正，代码则检验这些判断是否真的被做成了东西。

沿着 2025 年 6 月到 2026 年 7 月的内容看，可以提炼出六条相对稳定的主线。

第一，AI 对他首先不是效率工具，而是重新找回 Builder 身份的媒介。离开 PSPDFKit 后，他经历了明显的失重感，最终给出的答案不是“找到一个使命”，而是“目的要靠创造出来”。重新坐回电脑前、把想法做成东西，才让那股创造冲动回来。[1]

第二，他认为开发者价值正在从语法生产迁移到系统判断：选什么依赖、怎样划分边界、数据怎样流动、产品是否有感觉、Agent 偏离时如何拉回来。2025 年 6 月，他把这种变化概括为“语法淡出，系统思维发光”；到 12 月，他甚至坦言自己已经很少逐行读代码，但仍会掌握组件、结构和整体设计。[5][10]

第三，他把 Agent 工程理解为“闭合反馈回路”，不是堆更多 Agent。详细规格、第二上下文批判、最新文档、Agent 友好的 CLI、可恢复的工具报错，都是为了让模型能观察结果、发现偏差并继续修正。[2][3][7][8] 他对复杂编排一直保留怀疑：人往往才是瓶颈，而软件需要通过触摸、试用和迭代逐步成形。[10]

第四，他极度重视信任和连续性，甚至愿意用高权限换取无摩擦执行。2025 年 6 月的“Claude Code is My Computer”把 Agent 从编码助手提升成通用计算机界面。[5] 但这更像 Peter 的个人风险偏好，不是可以直接复制的安全准则；他本人也依赖小时级备份，并在 2026 年谈到大众化 Agent 时明确承认安全仍需更深入设计。[5][12]

第五，他不接受“用了 AI 就是 Slop”这种判断。AI 可以参与写作和代码，但价值、责任与品味仍由人承担；同时，他强烈反对未标注的自动回复冒充真人占用他人注意力。[9] 这说明他的分界线不是“是否使用 AI”，而是**是否有人类意图、投入、选择和责任**。

第六，2026 年他的关注点已经从个人高效开发，扩大到 Agent 的社会化基础设施：当 Token 不再稀缺，代码审查、安全检查、Issue 处理和维护可能成为持续运行的计算流；OpenClaw 则要在热度过后提升质量、扩充团队、建立非营利结构，并维持开放性。[12][15][16][17][18] 不过，“开放、独立”目前主要来自 Peter 和项目方的公开主张，不能仅凭这些话推导出治理已经完全独立。

今天最重要的结论是：**Peter 真正稳定的不是某个模型、工具或工作流，而是一种不断重做工作流的能力。** 他的公开内容最值得学的，也不是“照抄配置”，而是如何把新模型变成一轮可运行、可验证、可继续调整的产品实验。

## Introduction｜研究范围与阅读方法

今天不做“Peter 发过哪些帖子”的信息汇总，而是回答四个问题：他如何理解 AI 与创造；他怎样定义未来开发者的工作；他的观点在半年多时间里发生了哪些变化；哪些表达值得借鉴，哪些只适用于他的个人环境。

研究范围以 Peter 本人的博客和 X 为主，并用其公开项目、文章中的工作流细节和社区活动做语境补充。由于 X 的表达短、快、带情绪，本文不会把单条帖子当作永恒立场；如果博客与 X 出现不同说法，优先保留时间线，解释背后的模型能力、项目阶段或工作环境如何改变，而不是把它们强行合并。

还需要区分四个层次：文章和帖子中可直接确认的是**事实与本人主张**；“这些观点形成什么方法论”属于本文的**综合判断**；项目开放性、安全性和社会影响则需要外部材料才能完整评估，今天只指出待验证问题，留到明天进入社区评价、争议和反方视角。

## Main Analysis｜公开观点的演化与内在主线

### 一、公开内容不是宣言，而是一份高速更新的实验日志

Peter 的内容有一个鲜明特点：结论几乎总和“我最近实际怎么做”绑定。2025 年 8 月的工作流文章开头就提醒读者，这套流程仍在演化；他当时以 Ghostty、Claude Code、少量工具为主，较大的任务使用 Plan Mode，并让 GPT-5 审查计划。[4] 到 12 月，他的主力已转成 Codex，认为性能更强的模型可以先对话、读代码、搜索和共同制定计划，不再需要用 Plan Mode 暂时拿走编辑工具。[10][14]

这不是简单的自相矛盾，而是一个重要信号：**Agent 工作流的保质期很短。** 旧模型容易过早动手，于是需要 Plan Mode；新模型能更长时间探索和遵守指令，同一个机制就可能变成仪式性负担。Peter 的工作方法不是保卫某套最佳实践，而是持续删除已经失去必要性的中间层。

同样的变化也发生在并行规模上。2025 年 6 月，他常开至少三个 Claude 实例；8 月认为普通开发 1–2 个 Agent、测试或 UI 清理约 4 个比较合适；12 月则同时推进 3–8 个项目。[4][6][10] 2026 年 5 月，他进一步声称团队会在云端持续运行约 100 个 Codex 实例，思考“如果 Token 不再重要，软件应该怎样构建”。[15] 这几个数字不是一套固定配置，而是从个人并发、项目并发走向组织级持续计算的轨迹。

所以阅读 Peter 的第一条规则是：**所有方法都要带日期。** 文章的价值不在“他最后选了 Claude 还是 Codex”，而在他为什么换、换掉了什么摩擦、能力边界发生了什么变化。

### 二、AI 重新连接的不是职业，而是他的 Builder 身份

《Finding My Spark Again》是理解 Peter 后续所有技术观点的情感入口。离开经营 13 年的 PSPDFKit 后，他写到自己曾把公司当成身份，退出后则留下明显的空洞。旅行、搬家和各种体验没有替他找到稳定目的；真正的转折来自重新接受一件事：目的不是等着被发现，而是在创造中建立。[1]

因此，他对 AI 的兴奋不只是“代码更快了”。AI 降低了把想法转成可运行东西的阻力，使他重新进入高密度的创造循环：想到、构建、试用、修正、发布，再从反馈里产生下一轮想法。OpenClaw 最初也被他描述为一个为了学习 AI、寻找乐趣而做的 playground，后来才形成更大的影响。[12]

这里可以看出 Peter 与许多 AI 评论者的不同。他很少从宏观替代率开始，而是从“今天能不能做出昨天做不出的东西”开始。对他而言，Builder 的身份不是职位，也不只等于创办公司；它更接近一种持续把想法外化成产品的生活方式。2026 年面对把 OpenClaw 做成大公司的可能时，他公开表示那条路对自己并不兴奋，因为自己已经经历过一次漫长的公司建设；他更想继续做 Builder，并借助 OpenAI 把 Agent 带给更多人。[12]

这也解释了他的内容为什么总带有强烈的行动召唤：不要先等待完整理论，先做一个最小可用东西，通过真实使用获得下一步信息。

### 三、开发者价值迁移：语法淡出，系统、产品与品味上升

Peter 最广为传播的一条判断是：“syntax fades, system thinking shines。”[5] 如果只截取这句话，很容易被理解成“代码不用学了”。但结合他后续文章，含义更具体：代码生成成本下降后，难点会向更高层移动。

2025 年 8 月，他列出的真正难题是分布式系统设计、依赖和平台选择、面向未来的数据结构。[4] 12 月，他进一步强调语言生态、依赖维护状态、客户端与服务端边界、通信方式和数据流向仍需要投入研究和判断。[10] 这些问题之所以重要，是因为一次错误的高层选择会让 Agent 以更高速度生产更多错误方向的代码。

他还提出一个很有价值的反向诊断：开发者不一定要亲手敲下代码，才能感知糟糕架构。当一个本应简单的任务耗时异常、模型持续挣扎、修改扩散到太多地方时，这些现象本身就是抽象不佳的反馈。[10][13] 换句话说，Agent 不只是生产工具，也可以成为架构的“阻力计”。

但这种工作方式仍要求开发者知道系统长什么样。Peter 说自己不再读大部分代码，同时紧接着说明，他知道组件在哪里、系统如何组织、总体设计是什么。[10] 忽略后半句，就会把“高层掌控”误读成“完全不理解实现”。真正被弱化的是逐行输入和逐行审阅，不是责任、结构感与技术判断。

他在 Claude Code Anonymous 中提到，采用 Agent 最快的是兼具技术与产品能力的 full-breadth developers。[11] 这也支持同一结论：Agent 时代扩大价值的，不只是更强的编程技巧，而是能同时判断技术可行性、用户价值和产品完成度的人。

### 四、Context Engineering：好的规格、文档和工具要帮助 Agent 自我修正

Peter 的公开方法中，最可迁移的一部分是 Context Engineering，但它并不等于写更长的 Prompt。

在早期 Vibe Coding 工作流里，他强调规格越清楚，进入代码生成时的摩擦越小。[2] 在理解陌生代码库时，他会采用“两上下文”技巧：一个上下文产出设计或理解，另一个独立上下文专门找出二十个含糊、不一致或缺失的点，再把批评反馈给原上下文修订。[3] 这实际上把“生成”和“审稿”拆开，降低同一上下文对自己第一版答案的路径依赖。

文档必须是当前的。llm.codes 的出发点，就是把对 Agent 不友好的 Apple 文档转成可读取格式；Peter 直接指出，模型需要当前文档，而不是古老示例。[8] 到 12 月，他会为子系统维护 `docs/` 文档，并让 Agent 在相关任务里主动读取；他甚至明确说，代码库不再只为自己导航，而要让 Agent 高效工作。[10]

工具设计也遵循同一原则。他在 MCP Best Practices 中强调，配置错误不应让工具直接崩溃，而应返回足以让调用者自我修正的说明。[7] 这句话很重要：Agent 工具的好坏，不只看一次调用成功率，还看失败后是否能把有用状态带回下一轮推理。

这些做法可以归纳为一个闭环：**给 Agent 足够上下文 → 让它采取动作 → 返回可解释结果 → 用另一视角检查 → 更新长期文档。** 真正的 Context Engineering 是让系统持续获得正确上下文，而不是在开头塞进一大段静态说明。

### 五、“Less is more”：Agent 数量不是闭环质量

Peter 经常同时运行多个 Agent，却又对复杂多 Agent 编排保持怀疑，这两点并不冲突。他愿意并行的是边界清楚、可以独立推进的工作；他反对的是为了“Agentic”而增加额外状态、邮件、Issue 流转或编排层。

2025 年 8 月，他删除了最后一个常用 MCP，因为模型会在没有必要时启动 Playwright，既更慢又污染上下文；他更偏好已有成熟 CLI 的服务，只需在规则里告诉 Agent 如何调用。[4] 12 月，他仍认为很多自动任务管理系统没有必要，因为通常自己才是瓶颈。[10]

原因不是他排斥自动化，而是他的产品过程高度迭代。他往往只有大致方向，必须把东西做出来、触摸、试用、感受，再决定下一步。一个系统如果要求他一开始提交完整需求，之后在后台一次性交付，反而切断了最重要的产品反馈。[10]

因此，他推崇的不是“无人参与”，而是“人类注意力放在方向变化上”。Agent 可以承担长时间重构、测试、资料检索和机械性传播；人则持续判断产品有没有感觉、抽象是否自然、下一轮该往哪里走。对 Peter 而言，真正的吞吐量来自更短的反馈环，而不是更复杂的组织图。

### 六、信任是效率放大器，也是最危险的个人偏好

《Claude Code is My Computer》展示了 Peter 最激进的一面：他用跳过权限确认的模式运行 Claude Code，让它操作文件、Git、系统设置、密钥和发布流程。他认为持续审批会破坏对话与执行的连贯性，而完整文件系统、命令输出和迭代能力使 Agent 成为自然语言驱动的通用计算机界面。[5]

但文章也写明了前提：他知道恶意 Prompt 理论上可能破坏系统，并保留小时级快照和整盘克隆。[5] 这是一种“高信任 + 强恢复”的个人工程选择。它依赖单用户环境、较高技术能力、明确备份习惯和风险承受力，不应简化成“关闭权限提示能提升效率”。

到了 2026 年，当目标从自己能用变成“连我妈妈也能用”，Peter 的措辞明显变化：这需要更广泛的改变、更深入的安全思考，以及更前沿的模型与研究。[12] 这恰好暴露出个人 Agent 产品的核心张力：高手可以用知识、备份和警觉承担风险，普通用户需要产品本身提供更好的权限边界、解释、确认和恢复能力。

因此，他的两类公开观点要放在一起看：**对自己，他愿意用信任换连续性；对大众，他承认安全不能靠用户像他一样大胆。** 这不是已经解决的问题，而是 OpenClaw 下一阶段必须回答的问题。

### 七、AI 写作与 Slop：评判对象应是作品和责任，不是工具标签

2025 年 8 月，Peter 因为使用 Agent 协助博客写作，被 Lobsters 管理者以“startup slop”为由屏蔽域名。他的回应不是否认 AI 参与，而是公开工作过程，并主张按内容本身的价值判断：人可以不用 AI 写出 Slop，也可以借助 Agent 做出好作品，Agent 只是工具。[9]

但他并非认为一切自动内容都合理。他明确区分“AI 辅助表达”和“自动化冒充本人交流”：如果 X 回复或私信由自动化生成、没有标注，却使用真人头像直接占用他的注意力，他会认为这是对时间的不尊重。[9]

这条分界线可以概括为三问：内容背后是否有真实意图；作者是否投入了选择和修改；对方是否知道自己在与自动化交互。只要责任和身份被故意模糊，效率就会转化成注意力污染。

Peter 的博客本身也提供了一种可检查性：文章仓库、提交记录和编辑过程公开，让读者至少能看到产物如何形成。[9] 这不是 AI 写作争议的最终答案，但比“纯人工/纯 AI”二分法更接近实际创作过程。

### 八、2026 年的新命题：Token 不再稀缺后，软件工程会变成持续计算

2026 年 5 月，Peter 在 X 上提出一个更组织级的问题：“如果 Token 不重要，我们未来会怎样构建软件？”他随后称团队在云端持续运行约 100 个 Codex 实例，用于不断分析与处理工作。[15] 这里的“100”是 Peter 本人的公开陈述，本文没有独立审计其口径；更值得关注的是背后的假设变化。

过去，模型调用像稀缺专家时间，任务必须精挑细选；当成本和供给不再是首要约束，Agent 可以从“收到需求才写代码”扩展为持续审查代码、检查安全、整理 Issue、更新文档、寻找重复模式和主动维护。软件工程的单位可能从一次 Prompt，变成长期运行的计算流。

这种未来也会产生新瓶颈：谁来筛选 100 个 Agent 的发现，哪些建议可以自动执行，如何避免重复劳动与噪声，错误权限会造成多大爆炸半径。Peter 早期“人通常是瓶颈”的判断并没有消失，只是从个人窗口管理升级成组织级注意力和治理问题。[10][15]

### 九、OpenClaw、OpenAI 与“开放”的治理张力

2026 年 2 月，Peter 宣布加入 OpenAI，同时表示 OpenClaw 将进入基金会，保持开放和独立，并继续支持更多模型和公司；他的理由是，OpenAI 能让“把 Agent 带给所有人”的目标更快发生。[12][18] 6 月，他表示热度已经回落，项目在提升质量、扩充团队并创建非营利组织。[16] 7 月，他又用一句带自嘲意味的话强调，即使坐在 OpenAI 办公室里，“Open means open”。[17]

这些话显示，他知道外界会关注潜在冲突：一个强调用户数据所有权、模型选择和开放生态的项目，其核心人物同时加入一家大型模型公司。Peter 给出的解决方案是基金会、独立性和多模型支持。

但研究上必须保留边界：**本人承诺是重要证据，却不是制度事实的全部。** 是否真正独立，要看基金会法律结构、治理席位、商标与仓库控制、资金来源、发布权限、模型中立性和社区决策机制。今天能确认的是他的公开立场与正在推进的方向，不能确认的是所有治理承诺已经完成并经受长期检验。

| 2026 年关注点已从个人开发扩展到持续 Agent 基础设施与大众化 | 100 Codex、OpenClaw 基金会与安全使命 [12][15][16][18] | 中高；规模数字未独立核验 |
| OpenClaw 的开放性同时存在承诺与治理张力 | 本人加入 OpenAI、基金会与“Open means open”声明 [12][17][18] | 中；制度独立性仍待外部核验 |

## Counterevidence Register｜反证与不同解释

第一，“很少读代码”不能被外推为所有开发者都无需读代码。Peter 同时说明自己仍掌握组件、结构和总体设计；他的个人项目、长期经验、备份与快速返工能力，也和多人协作、受监管系统或高安全软件不同。[10]

第二，模型挣扎可能提示坏架构，但也可能来自知识截止、工具故障、上下文缺失、任务描述含糊或模型能力不足。不能把每次失败都当成重构代码的理由。[7][8][13]

第三，多 Agent 和高 Token 消耗展示了上限，却没有单独证明经济收益。约 100 个云端 Codex 实例是 Peter 的公开说法，缺少任务口径、有效产出率、重复率和人工审核成本，不能直接转换成“团队规模被等量替代”。[15]

第四，跳过权限确认依赖 Peter 的风险偏好和备份体系。即使两个月没有事故，也不能证明恶意输入、供应链攻击或误操作风险可以忽略；历史无事故不是安全保证。[5]

第五，“AI 只是工具”强调作者责任，但没有完全回答平台端海量低成本内容带来的信息污染、搜索质量下降和社区审核成本。个体作品可能有价值，生态层面的外部性仍然存在。[9]

第六，加入 OpenAI 可能为 OpenClaw 带来模型、研究和资源，也可能增加路线依赖。基金会与开放承诺是积极信号，但要由长期治理结构、发布实践和多模型兼容性验证。[12][17][18]

## Synthesis｜Peter 的公开思想可以怎样理解

把这些内容放在一起，Peter 的 AI 世界观不是“模型将替代程序员”，而是一个四层结构。

最底层是**创造观**：目的通过把想法做成东西而建立，AI 的意义在于恢复和扩大这种创造能力。[1]

第二层是**能力观**：代码语法变便宜，系统边界、依赖、品味、产品判断和责任变贵。开发者不会因少打代码而自动失去价值，但必须上移到更高层的掌控。[4][5][10]

第三层是**工程观**：Agent 要拥有可读的当前文档、可调用的 CLI、可恢复的报错和能够验证结果的闭环；工具越多不等于效率越高，能否继续修正才是关键。[2][3][7][8]

最上层是**产品观**：真正改变生活的 Agent 不能停在 IDE 中，它会进入消息、电脑、家庭设备和日常流程；而能力扩张最终会逼迫产品重新设计权限、安全、身份和治理。[5][12]

最值得关注的是，这四层并非已经封闭完成。Peter 的表达里保留了大量变化和张力：既信任 Agent 到跳过权限，又强调大众化需要安全；既同时运行许多 Agent，又认为复杂编排常常多余；既加入 OpenAI，又强调 OpenClaw 必须开放独立。这些张力不是报告需要抹平的噪声，反而是理解 AI Builder 在真实变化中如何做选择的核心材料。

## Limitations｜限制与仍待验证的问题

本篇高度依赖 Peter 本人的博客、X 和项目陈述，最适合还原他的自我叙事、工作方法和公开立场，不足以独立评估实际生产率、代码质量、安全事故率或基金会治理效果。明天需要加入采访者、合作者、社区维护者、批评者和独立技术分析的材料。

X 帖子的文字很短，语境和后续讨论可能改变其含义；部分帖子通过公开嵌入接口核对正文，但没有系统抓取全部回复链。本文因此把它们作为“当时立场快照”，不作为完整论证。

Peter 的工作环境也很特殊：资深工程背景、单人或小团队项目、强恢复能力、多个设备和高 Token 预算。文中方法不能直接外推到大团队、关键基础设施、金融医疗系统或普通非技术用户。

最后，2026 年 OpenClaw 与 OpenAI 相关信息仍在快速变化。基金会状态、团队规模和 Agent 基础设施可能继续调整；本文按 2026-07-17 可见信息记录，并对未独立核验的说法明确保留。

## Recommendations｜对用户的具体启发

第一，建立“带日期的方法库”。记录自己每月的模型、工作流、有效机制和已删除机制，不把任何最佳实践写成永久规则。每次模型升级时，优先检查哪些中间层已经可以删掉。

第二，把 Agent 失败当作诊断信号，但先做四分法：是需求不清、上下文缺失、工具不可恢复，还是架构本身不自然。只有最后一种才直接指向重构。

第三，为项目增加 Agent 可读性。给关键子系统维护短文档，提供最新示例，让工具报错包含下一步修正方式；能用稳定 CLI 闭合的流程，不必先引入复杂 MCP 或编排平台。

第四，把人的注意力留给产品判断。让 Agent 处理检索、重构、测试、迁移和重复工作；自己持续试用结果，判断是否自然、是否解决真实问题、下一轮方向是否改变。

第五，不照抄 Peter 的高权限设置。学习的是“连续执行 + 可恢复”，而不是单独关闭确认。普通工作环境至少要同时考虑最小权限、隔离、备份、审计和人工确认。

第六，发布 AI 辅助内容时保留作者责任：明确自己的核心判断，检查事实和语气，必要时说明工具参与；自动化直接与他人交流时，应让对方知道面对的是 Agent。

第七，为未来的常驻 Agent 设计“注意力预算”。当并发数量从 3 个变成 100 个，真正稀缺的是审核、去重、优先级和授权。先定义哪些发现只记录、哪些需要确认、哪些允许自动执行，再扩大并发。

第八，研究 Peter 这类人物时，把“他说了什么”和“后来做成了什么”配对。X 适合发现最新假设，博客适合理解方法，代码和产品才适合验证这套假设有没有形成真实能力。

## Methodology｜方法说明

本次先以 Asia/Shanghai 确认研究日期，再检索 Peter 的个人网站、博客源码索引和 X 公开内容。来源登记 18 项，均为 Peter 本人发布的一手材料；针对身份与创造、开发者价值、Context Engineering、工具最小化、AI 写作、OpenClaw 治理六类主题，各保存至少一条可定位证据。

分析采用“时间线 + 主题聚类”两步法。先按 2025 年 6 月、8–9 月、12 月和 2026 年 2–7 月排列工作流变化，再识别跨时间相对稳定的创造观、能力观、工程观和产品观。对 Plan Mode、主力模型和并发数量等变化，不强行求一致，而是解释为模型能力和项目阶段变化下的方法更新。

事实、本人主张和本文判断被分别处理：文章发布日期、原话和公开选择属于可核查事实；效率、安全、治理效果等若只有本人陈述，则标为未独立核验；“实验日志”“阻力计”“四层世界观”等是本文综合概括。报告同时保留六类反证，避免把高经验、高权限、高预算的个人流程普遍化。
