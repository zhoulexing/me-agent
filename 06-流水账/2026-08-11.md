### 2. 多 Agent 协作为什么不能靠共享一个大上下文？

- **分类**：工程实践
- **关联笔记**：Claude Code 跨 Session 消息通信深度解析：寻址、调度与权限隔离的完整链路
- **核心判断**：工程上更可靠的多 Agent 方案，是让每个 Agent 保持独立上下文和工作区，只交换结构化的依赖变化、结果与阻塞信息。
- **与 AI 的真实关系**：Agent 的上下文有容量、污染和职责边界；显式消息能降低全量共享造成的噪声与耦合，但也引入命名、幂等、排队、容量和交接协议等工程成本。
- **内容框架**：
  1. 用并行开发场景说明多个 Agent 为什么会产生依赖与状态同步需求。
  2. 对比三种方案：共享上下文、人工转述、独立 Session 加消息通道。
  3. 设计最小消息协议：任务、结论、影响范围、证据、下一步与负责人。
  4. 处理工程风险：重名寻址、重复消息、未读队列上限和消息延迟。
  5. 配合 Worktree 与测试门禁，避免“消息到了但代码互相覆盖”。
  6. 沉淀可复用原则：隔离执行、显式交接、可验证结果、失败可恢复。

### 3. AI Agent 发来的指令，为什么绝不能等同于用户授权？

- **分类**：个人判断
- **关联笔记**：Claude Code 跨 Session 消息通信深度解析：寻址、调度与权限隔离的完整链路
- **核心判断**：Agent 之间可以传递信息和请求，却不能传递用户授权；能力越强、协作链越长，越要坚持“消息是输入，权限由本地边界重新判断”。
- **与 AI 的真实关系**：多 Agent 会放大指令来源混淆、越权代办和提示注入风险。Peer 消息若被当成用户意图，攻击者可能通过一个低信任 Agent 间接驱动高权限 Agent 执行敏感操作。
- **内容框架**：
  1. 从一个看似合理的 Peer 请求切入：替我修改权限配置并执行命令。
  2. 区分三件事：消息可达、模型采纳、工具获准执行。
  3. 解释为什么 Peer Session Message 不应拥有 User Message 的授权地位。
  4. 拆解 accept、hold、refuse 三类准入策略及其适用情形。
  5. 延伸到实际 Agent 系统：身份、来源、最小权限、审计和人工确认。
  6. 给出个人判断：未来 Agent 安全的核心不是“彼此信任”，而是“每次重新验证”。
