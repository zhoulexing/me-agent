## AI 视频选题

### 1. MCP 有了 Tools 和 Resources，为什么还需要 Skills？

- **分类**：技术解释
- **关联笔记**：MCP Skills 扩展深度解析：把工作流知识变成协议标准
- **核心判断**：Skills 扩展标准化的是工作流指令的发现和分发，而不是替 Agent 执行工作流，更不是把远端指令自动变成可信操作。
- **与 AI 的真实关系**：Agent 需要知道工具能做什么、数据在哪里，也需要知道如何组合两者完成任务；扩展正是为这层可复用知识定义协议绑定。
- **内容框架**：
  1. 从“工具已接入，Agent 却仍不知道按什么步骤完成任务”的问题切入。
  2. 分层解释 Tools、Resources、Skills 各自提供能力、数据与工作流指令。
  3. 说明 `skills/list`、`skills/get` 与可选的 `resources/directory/read` 分别解决什么发现问题。
  4. 用 URI、frontmatter、文件清单和摘要解释 Skill 条目的结构；文件内容仍走 `resources/read`。
  5. 划清传输与激活：读取不等于执行，摘要验证也不等于来源可信；审批由宿主负责。
  6. 落回结论：协议降低分发摩擦，但运行可靠性还取决于宿主实现与任务验收。

### 2. 团队把 Skill 放到 MCP 服务器，宿主该怎样安全加载？

- **分类**：工程实践
- **关联笔记**：MCP Skills 扩展深度解析：把工作流知识变成协议标准
- **核心判断**：集中分发能减轻版本漂移，却把来源识别、内容校验、审批和回滚变成宿主必须承担的工程责任；这应先做小范围验证，而非一接入就自动启用。
- **与 AI 的真实关系**：Skill 指令会进入 Agent 的上下文并影响工具使用，分发与激活链路直接决定 AI 系统的行为边界和可审计性。
- **内容框架**：
  1. 设定待验证场景：多个 Agent Runtime 复用同一套工作流；这是方案讨论，不冒充已实施项目。
  2. 对比各端手工安装的成本：重复维护、版本不一致和更新难追踪。
  3. 拆解远端链路：服务器声明能力、宿主发现条目、读取所需文件。
  4. 设计加载闸门：以服务器身份加 URI 标识来源，检查摘要与大小，处理同名冲突，再审批激活。
  5. 讨论代价与异常：网络不可用、动态内容无稳定摘要、内容变更后的刷新和回滚。
  6. 给出试点验收：记录加载版本、审批人、任务结果与失败恢复，再决定是否扩大分发。

### 3. 工作流知识进入协议，Agent 就会更可靠吗？

- **分类**：个人判断
- **关联笔记**：MCP Skills 扩展深度解析：把工作流知识变成协议标准
- **核心判断**：把“怎么做”做成可分发的标准，解决的是知识到达问题；任务能否稳定完成，仍要靠边界、反馈、验收和失败恢复来证明。
- **与 AI 的真实关系**：Agent 不只是读取说明，还会依据说明调用工具、改变外部状态；指令供给与任务闭环之间存在真实的因果链和治理缺口。
- **内容框架**：
  1. 以“连接服务器后，Skill 就跟着到位”的便利性作真实触发。
  2. 提出核心矛盾：说明可分发，不代表模型理解正确或执行结果合格。
  3. 区分三层问题：能发现指令、能按权限执行、能通过结果验证。
  4. 结合既有认知：AI 放权前先搭确定性框架，明确输入、工具权限、反馈和验收。
  5. 给出可行动的检验：针对关键任务做回放、失败注入与人工复核，观察成功率和恢复能力。
  6. 收束判断：标准化值得做，但不要把协议覆盖率当成 Agent 的任务完成率。
