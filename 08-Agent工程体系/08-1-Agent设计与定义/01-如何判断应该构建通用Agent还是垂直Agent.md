# 如何判断应该构建通用 Agent 还是垂直 Agent

## 1. 这个课题解决什么问题

在开始设计 Prompt、Tool、Skill 或 Workflow 之前，明确 Agent 对外承诺的任务空间，以及应当采用通用入口、垂直执行器，还是两者组合的形态。

本课题解决“做什么问题”的边界，不解决“已选定能力该由 Tool、Skill、Subagent 还是 Workflow 实现”的问题，也不直接规定每项动作的权限策略。

## 2. 为什么会出现这个问题

“通用”和“垂直”常被误当成模型能力、工具数量或工程成熟度的高低之分，于是会出现两类错误：

- 将所有可能有用的工具、知识和权限塞给一个入口，造成上下文膨胀、误调用、权限扩大和验收失焦。
- 因为当前只能做少数流程，就把本可通过规划和组合解决的开放任务过早固化为大量 Workflow。

更根本的错误是：以“模型大概能理解”为准对外承诺能力，而不是以“系统能稳定交付结果”为准定义边界。

## 3. 核心概念

- **参照任务空间（U）**：讨论通用或垂直时所使用的问题全集，例如“全部企业任务”或“软件开发任务”。没有 U，通用/垂直没有确定含义。
- **可承诺任务集合（A）**：系统在明确质量阈值内可以接受并交付的任务集合。
- **通用 Agent**：相对于 U，能够可靠处理较大、较异构且部分不可预先枚举的任务集合，并能在约束内处理新变体的 Agent。
- **垂直 Agent**：相对于 U，聚焦于边界较明确的任务子集，并对该子集做更深的知识、流程、工具或控制优化的 Agent。
- **任务空间边界**：哪些问题应由 Agent 受理和处理；用于讨论通用性。
- **行动权限边界**：即使已理解问题，Agent 被允许执行到什么程度；用于控制风险，不用于单独判断通用或垂直。
- **结果闭环**：有可观察的结果证据，能够判断是否满足目标；不等于模型说“已完成”。

通用/垂直与工程成熟度是两条独立坐标。一个垂直 Agent 可以没有闭环能力；一个任务范围较广的 Agent 也可能具备成熟的验证和恢复机制。

## 4. 系统边界

| 项目 | 内容 |
| --- | --- |
| 输入 | 目标用户、候选任务分布、领域约束、风险、权限、验收方式、演进预期 |
| 输出 | AgentScopeContract：参照任务空间、受理范围、排除范围、未知任务处理方式和结果承诺 |
| 上游 | 产品定位、业务流程、合规要求、用户授权、已有系统能力 |
| 下游 | 能力边界、Tool/Skill/Subagent/Workflow 选型、权限策略、评测集和生产治理 |

“任务空间边界”和“行动权限边界”必须分别表达：前者决定一个问题是否值得被受理，后者决定它能否被直接执行、需要审批，还是需要转交。

## 5. 核心争议

真正的问题不是“通用好还是垂直好”，而是：

> 在哪个参照任务空间内，系统应承诺哪些结果；面对设计时未枚举的任务，是由它受限探索、明确拒绝，还是转交给专用执行器？

不存在脱离场景的标准答案。任务是否稳定、失败代价、可用权限、可验证性和新任务出现频率，都会改变最优架构。

## 6. 候选方案与决策维度

| 候选方案 | 适用条件 | 收益 | 主要代价 |
| --- | --- | --- | --- |
| 固定 Workflow 集合 | 流程稳定、输入结构化、异常少 | 确定性高，易审计和评测 | 新任务需要开发，覆盖面受目录限制 |
| 垂直 Agent | 领域稳定，需深知识或专用工具 | 领域效果、控制与验收更强 | 跨域任务需要路由或转交 |
| 单一通用 Agent | 任务高度开放、低风险、共享工具足够 | 入口简单，适应新变体快 | 上下文、权限、验证和故障隔离困难 |
| 通用入口 + 垂直 Agent/Workflow | 用户入口广，执行领域差异大 | 兼顾开放理解与确定性交付 | 需要路由、协议和统一治理 |

关键决策维度：

- 任务能否被完整枚举；
- 任务之间是否异构，是否需要跨能力组合；
- 未知任务的出现频率与价值；
- 结果是否可验证，失败是否可恢复；
- 直接行动的风险与授权成本；
- 新增一个任务时，修改代码、注册能力和重新评测的成本。

## 7. 系统不变量

1. 所有“通用/垂直”的判断必须显式写出参照任务空间 U。
2. 不得以 Tool 数量、Prompt 长度或模型知识量替代任务覆盖判断。
3. 对外承诺必须以可靠交付为准，不得把“模型可以尝试”写成“系统能够完成”。
4. 对未知任务的探索与产生真实副作用的执行必须分开控制。
5. 权限不足、风险不可接受、结果不可验证或失败不可恢复时，不得自主扩大行动范围。
6. 通用入口不等于所有执行都由同一个 Agent 完成；它可以路由到垂直 Agent 或确定性 Workflow。

## 8. 工作机制

设计阶段按以下顺序形成范围契约：

1. **声明 U**：先明确比较范围，例如“软件开发任务”，而不是笼统说“面向程序员”。
2. **拆分任务类型**：识别任务目标、输入、外部系统、副作用和验收证据。
3. **划定 A**：只把已具备能力、授权、验证与恢复条件的任务放进承诺范围。
4. **处理未知任务**：允许在只读、低风险或沙箱环境中探索；在无法满足约束时澄清、拒绝或转交。
5. **选择执行形态**：稳定且高风险的部分优先确定性 Workflow；需要领域深度的部分交给垂直 Agent；跨域开放理解由通用入口承担。
6. **写入 AgentScopeContract**：将受理范围、排除范围、路由规则和结果承诺版本化，并作为评测集边界。

因此，可承诺的任务不是模型认知能力的并集，而是可交付条件的交集：

\[
可承诺任务 = 任务覆盖 \cap 已授权行动 \cap 风险可接受 \cap 结果可验证 \cap 失败可恢复
\]

## 9. 案例

### 场景

团队考虑两种产品：

- 员工助手：覆盖人事、财务、IT、采购、行政等员工工作问题；高风险动作需要审批。
- Java 代码审查助手：只审查 Java Pull Request，不承担编码、调试或部署。

若以“全部企业任务”为 U，二者都只是子集；不能因为一个服务员工、另一个服务程序员，就直接得出通用或垂直的结论。

### Harness 行为

团队分别声明参照空间：

- 对员工助手，U 为“员工工作任务”。它可以作为广入口理解不同部门问题，并将高风险或强领域任务路由到专用执行器。
- 对代码审查助手，U 为“软件开发任务”。它只覆盖其中的 Java 审查子集，因此是垂直执行器。

员工助手收到“导出全员薪资并发送到外部邮箱”这一未预设请求时，可以探索可用能力和政策，但不能把探索升级为实际导出和外发：权限不足与风险过高会阻止执行。

### 结果

系统没有把“模型能理解薪资问题”当作交付承诺。它输出拒绝或审批路径，并记录这是权限/风险阻断，而不是把失败伪装成能力缺失。

### 结论

案例说明：通用性取决于相对任务空间和可靠覆盖，而不是用户身份或工具数量；开放探索不等于无边界执行。

它不能推出：员工助手一定比代码审查助手更通用。改变参照任务空间 U，分类可能随之改变。

## 10. 伪代码

以下为说明性伪代码，不代表现有项目已经实现该能力。

```python
def decide_agent_shape(candidate_tasks, reference_space, controls):
    # 输入：候选任务、参照任务空间与系统控制条件
    accepted = []
    transfers = []

    for task in candidate_tasks:
        can_deliver = (
            task in reference_space
            and has_reliable_capability(task)
            and controls.is_authorized(task)
            and controls.risk_is_acceptable(task)
            and controls.has_verification(task)
            and controls.has_recovery_path(task)
        )

        if can_deliver:
            accepted.append(task)
        elif can_explore_safely(task, controls):
            transfers.append(plan_exploration_or_delegation(task))
        else:
            transfers.append(refuse_or_request_approval(task))

    # 副作用：固化为版本化范围契约，供路由和评测使用。
    contract = persist_scope_contract(reference_space, accepted, transfers)
    return choose_architecture(contract)  # workflow / vertical / general-entry-plus-specialists
```

## 11. 失败案例或反例

### 反例一：把“模型懂”当成“产品能做”

企业助手能解释薪资规则，于是产品宣称可“自动处理薪资事务”。当用户要求修改工资时，系统既无授权也无回滚和验收证据，只能在执行后暴露风险。

问题不在模型理解，而在承诺集合 A 超过了可交付集合。

### 反例二：用 Workflow 数量衡量通用性

系统拥有 1,000 个固定报表流程，却不能处理任一未定义的组合需求。它的固定覆盖可以很大，但在开放任务空间中未必通用。

### 反例三：把通用入口做成万能执行器

一个入口同时拥有 HR、财务、生产、数据导出和部署权限。它虽然能理解跨域请求，却扩大了误调用面、敏感数据面和失败恢复范围。

## 12. 设计选择与权衡

- **选择垂直 Agent**：适合高错误成本、强领域知识、流程和验收稳定的任务。代价是新领域要新增专用能力。
- **选择通用 Agent**：适合任务开放、信息检索和计划组合价值高、低风险探索可接受的场景。代价是必须投入上下文、路由、权限和验证治理。
- **选择通用入口 + 垂直执行**：适合企业助手等宽入口场景。代价是要定义清楚入口的职责：理解、澄清、路由，而非默认拥有所有副作用权限。

通常先按“可承诺任务”建立边界，再决定架构；不能先选“通用”这一标签，再倒推给它添加无限能力。

## 14. 如何验证这套机制

- 为每个 AgentSpec 写出 U、A、排除任务和未知任务策略，并让产品、业务与安全共同评审。
- 评测集同时包含已知任务、跨域组合任务、未枚举变体、越权请求和不可验证任务。
- 观察拒绝、审批、转交与成功完成是否分别有结构化原因和结果证据。
- 新增任务时，记录它是扩展 A、增加垂直执行器，还是新增 Workflow；避免无理由地扩张主 Agent 权限。

## 15. 面试追问与评分要点

**追问一：一个代码 Agent 能否既是“软件开发领域的通用 Agent”，又是“企业全部任务中的垂直 Agent”？**

优秀回答：指出通用/垂直必须相对于 U 定义，并能说明同一系统在不同 U 下分类不同。

**追问二：一个拥有 1,000 个 Workflow 的系统，是否一定比覆盖 100 个任务类型的 Agent 更通用？**

优秀回答：区分固定覆盖、任务异构度、开放性、迁移能力与可靠性；不只比较数量。

**追问三：未知任务应该总是由通用 Agent 自行尝试吗？**

优秀回答：区分低风险探索与真实执行，说明权限、风险、验证和恢复如何共同限制副作用。

**追问四：为什么“模型能够理解”不能成为产品能力边界？**

优秀回答：把能力承诺落到权限、可验证结果和恢复条件，而不是只讨论模型知识。

## 16. 延伸问题

- 如何量化任务空间的异构度和开放性，而不只靠主观描述？
- 面对长尾任务，何时应该扩展通用 Agent，何时应该新增垂直 Agent 或 Workflow？
- 路由器如何估计自己是否应转交，而不因错误自信造成越权或误分派？
- 可承诺任务集合如何随模型、工具、权限和验证器版本变化而自动重新评测？
