# 用户目标、约束与验收标准

## 1. 这个课题解决什么问题

这个课题解决的是：Harness 如何把用户的一段自然语言请求，整理为可执行、可约束、可验证的目标定义。

它不负责执行具体计划，也不负责最终验证；它负责为后续规划、执行和验证提供共同依据。

## 2. 为什么会出现这个问题

用户通常描述的是动作，不一定直接描述真实目标。

例如用户说“重启服务”，可能真正想要的是“让业务接口恢复正常”。如果 Agent 把重启命令执行成功当作任务完成，就会把动作成功误认为目标成功。

自然语言请求还可能缺少：

- 明确的完成条件；
- 不能触碰的边界；
- 风险和影响范围；
- 当前环境状态；
- 需要用户确认的歧义。

## 3. 核心概念

### Request

用户原始说法。例如：“帮我重启一下登录服务。”

### Action

为了达到目标采取的动作。例如：执行重启命令。

### Goal

用户真正希望现实世界达到的状态。例如：用户能够正常登录。

### Constraint

完成目标过程中必须遵守的限制。例如：不能修改用户密码，不能降低鉴权强度。

### Acceptance Criteria

能够被观察或验证的完成条件。例如：正确账号登录成功、错误密码仍然被拒绝、相关测试通过。

核心关系是：

```text
用户请求
→ 识别真实目标
→ 提取约束
→ 建立验收标准
→ 为计划和验证提供依据
```

## 4. 系统边界

这个课题的上游是用户输入、Agent 角色、当前环境和领域知识；下游是计划生成、行为控制和目标验证。

目标理解可以提出候选计划，但计划生命周期、步骤调度和验收执行属于本领域后续的“任务编排”和“目标验证”课题。

## 5. 核心争议

核心争议不是“要不要理解用户”，而是 Harness 应该在多大程度上推断用户未明确表达的目标。只执行字面动作会丢失真实目的，过度推断又可能扩大授权范围。

## 6. 候选方案与决策维度

- **字面动作模式**：只执行用户明确指定的动作，确定性高，但容易把动作完成误认为目标完成。
- **模型自由推断模式**：体验流畅，但可能引入未经授权的目标、约束或副作用。
- **GoalSpec 模式**：由模型提出目标、约束和验收标准，再由 Harness 根据风险决定直接采用、记录假设或请求澄清。

选择时需要考虑歧义是否改变副作用、权限、成本、完成标准和失败后果。

## 7. 系统不变量

- 不能把模型推断的目标扩展当成用户授权。
- 用户明确约束必须进入后续计划和验证。
- 高风险歧义没有澄清前不能执行不可逆动作。
- 验收标准必须能够观察或明确标记为需要人工判断。

## 8. 工作机制

一份最小目标定义至少包含：

```yaml
goal: 用户希望最终达到的状态
constraints: 执行过程中必须遵守的边界
acceptance_criteria: 可以验证的完成条件
unknowns: 当前仍不明确但可能影响结果的问题
```

当歧义会显著改变目标、风险或副作用时，Harness 应要求澄清；不会改变关键结果时，可以记录合理假设后继续。

## 9. 案例

### 场景

用户说：

```text
帮我重启一下登录服务。
```

### Harness 行为

Harness 不把“运行重启命令”直接定义为最终目标，而是整理出：

```yaml
goal: 恢复登录服务的业务能力

constraints:
  - 不修改用户密码
  - 不关闭现有鉴权检查
  - 不扩大生产变更范围

acceptance_criteria:
  - 服务进程正常运行
  - 健康检查通过
  - 正确账号可以登录
  - 错误密码仍然被拒绝
```

### 结果

即使重启命令退出码为 `0`，只要登录接口仍然失败，任务就不能被标记为完成。

### 结论

用户请求中的动作可以成为计划步骤，但不能自动等同于用户目标。目标定义必须能够支撑后续的独立验证。

## 10. 伪代码

下面是说明性伪代码，不代表某个项目的现有实现：

```python
from dataclasses import dataclass


@dataclass
class GoalSpec:
    goal: str
    constraints: list[str]
    acceptance_criteria: list[str]
    unknowns: list[str]


def build_goal_spec(user_request, agent_role, current_state, domain_rules):
    intent = extract_intent(user_request, current_state)
    constraints = merge_constraints(
        agent_role.constraints,
        domain_rules.constraints,
        intent.explicit_constraints,
    )
    criteria = derive_observable_criteria(intent.goal, domain_rules)
    unknowns = find_material_ambiguities(intent, current_state)

    if contains_high_risk_ambiguity(unknowns):
        return request_user_clarification(unknowns)

    return GoalSpec(
        goal=intent.goal,
        constraints=constraints,
        acceptance_criteria=criteria,
        unknowns=unknowns,
    )
```

## 11. 失败案例或反例

错误处理方式：

```text
用户要求重启服务
→ Agent 执行 restart
→ 命令返回 0
→ Agent 宣布登录问题已经修复
```

这里缺少业务目标和验收标准，因此只能证明命令执行完成，不能证明用户问题已经解决。

## 12. 设计选择与权衡

### 每次都询问用户

目标更准确，但交互成本高，容易阻断简单任务。

### 完全由模型推断

体验流畅，但可能把隐含假设当成用户授权。

### 分级处理

低风险歧义记录假设后继续；会改变副作用、权限或验收结果的歧义必须询问。通常更适合作为通用策略。

## 14. 如何验证这套机制

可以建立以下测试：

- 用户只描述动作时，能否识别更上层目标；
- 是否保留用户明确提出的限制；
- 是否把验收标准表达成可观察状态；
- 高风险歧义是否要求用户确认；
- 是否避免把工具返回成功直接映射成目标成功。

## 15. 面试追问与评分要点

### 面试追问

- 用户只要求“重启服务”，系统能否自行修改配置或回滚版本？
- 什么类型的歧义可以记录假设后继续，什么类型必须询问？
- 用户中途修改目标时，旧 GoalSpec、计划和审批如何失效？
- 如何防止模型生成对自己过于有利的验收标准？

### 评分要点

优秀回答应区分 Request、Action、Goal 和 Outcome，说明授权边界、风险分级、验收来源，以及 GoalSpec 如何驱动计划、权限和验证。
