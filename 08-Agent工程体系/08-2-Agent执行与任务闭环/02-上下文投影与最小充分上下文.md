# 上下文投影与最小充分上下文

## 1. 这个课题解决什么问题

这个课题解决的是：Harness 如何从 Session、事件、文件、工具结果和外部系统中，选出模型完成当前决策所需的最小、准确、安全、可追溯信息。

它不是简单地把所有历史拼接进 Prompt，也不是只追求把文本压缩得更短。

## 2. 为什么会出现这个问题

Agent 系统掌握的信息通常远多于模型当轮需要看到的信息。全部放进上下文会导致：

- Token 和延迟增加；
- 无关信息干扰决策；
- 过期信息与真实状态冲突；
- API Key 等敏感信息泄露；
- 原始日志淹没真正重要的结果；
- 上下文压缩后丢失目标、约束或已发生的副作用。

## 3. 核心概念

### Event Log

记录真实发生过的事件，用于审计、回放和状态重建。

### Current State

根据事件和外部权威来源计算出的当前状态。

### Context Projection

从系统状态中生成的模型可见视图，只包含当前推理需要的信息。

### Turn Context Snapshot

模型在某一轮实际看到的冻结上下文，用于解释它为什么在当时作出某个决定。

### Minimum Sufficient Context

足以支持下一步正确决策，但不包含无关、过期、危险或重复信息的上下文。

## 4. 系统边界

上下文投影读取 Session、事件、Memory、工具结果和外部状态，输出模型可见上下文。

原始事件持久化、模型请求调度、权限和敏感信息过滤分别由本领域的“状态恢复”“执行循环”和“运行时控制”课题继续展开。

## 5. 核心争议

核心争议是：模型上下文应该尽量完整，还是应该由 Harness 主动选择和重写。完整历史更容易追溯，但成本和噪声不断增加；摘要更高效，却可能扭曲事实和丢失约束。

## 6. 候选方案与决策维度

- **完整历史模式**：实现简单、信息保留充分，但容易超限和污染决策。
- **摘要替代模式**：Context 小，但摘要错误可能成为新的错误事实来源。
- **事件源加投影视图模式**：保留不可变事实，为每轮生成最小充分视图，代价是需要维护事件、当前状态和投影的一致性。

选择时需要考虑任务时长、信息变化速度、可追溯要求、敏感性、Token 预算和恢复要求。

## 7. 系统不变量

- 用户目标、有效约束和已发生副作用不能在压缩中丢失。
- `UNKNOWN` 不能被摘要为 `SUCCESS`。
- 敏感凭证不能因为与任务相关就直接进入模型 Context。
- 关键结论必须可以追溯到事件、工具结果或外部权威来源。

## 8. 工作机制

```text
用户目标与约束
       +
Session 与 Event Log
       +
外部权威状态
       +
按需检索的知识
       ↓
状态对账
       ↓
相关性筛选
       ↓
敏感信息过滤
       ↓
压缩、摘要与引用
       ↓
一致性检查
       ↓
Turn Context Snapshot
```

筛选时至少判断：决策相关性、当前有效性、来源权威性、安全可见性和可追溯性。

## 9. 案例

### 场景

Agent 创建订单时，订单系统已经创建成功，但进程在收到响应前崩溃。旧对话停留在：

```text
我准备创建订单。
```

### Harness 行为

恢复后，Harness 不直接复用旧对话，也不修改原始事件。它先查询订单系统，确认订单已经存在，然后追加恢复事件并生成新的上下文投影：

```text
用户要求创建订单。此前执行期间发生中断。
恢复后已通过订单系统确认订单 12345 创建成功。
不要重复创建；下一步继续处理订单创建后的工作。
```

API Key、内部审批凭证、完整重试日志和 Token 统计不进入模型上下文。

### 结果

模型获得了继续决策需要的事实，同时不会因为旧历史重复创建订单，也不会接触不必要的敏感信息。

### 结论

Event Log 保存真实过程，Current State 表达当前事实，Context Projection 为模型生成面向本轮决策的视图。三者不能混为一体。

    current_state = replay_events(session_events)
    current_state = reconcile_with_authoritative_sources(

## 11. 失败案例或反例

### 把所有信息塞入 Context

完整工具日志、重复错误和大文件内容挤占窗口，模型反而忽略用户目标和关键约束。

### 只保留整理后的故事

如果删除原始事件，就无法判断摘要是否失真，也无法在恢复或审计时重建真实过程。

### 把 UNKNOWN 总结成 SUCCESS

外部状态没有确认时，摘要却写成“订单创建成功”，会让模型在错误事实基础上继续行动。

## 12. 设计选择与权衡

### 原样保留全部历史

可追溯性强，但上下文成本高、噪声大。

### 只保留摘要

模型上下文小，但摘要一旦错误就缺少恢复依据。

### 原始事件持久化，模型使用投影视图

同时保留追溯能力和上下文效率，但需要维护事件、状态和投影之间的一致性。

## 14. 如何验证这套机制

可以建立以下测试：

- 长历史下是否仍然保留用户目标和约束；
- 工具日志压缩后是否保留最终结果和关键错误；
- 外部状态变化后是否替换过期 Context；
- API Key、Token 和审批凭证是否不会进入模型上下文；
- `UNKNOWN` 是否始终保持为不确定状态；
- 每个关键结论是否能够追溯到事件或外部事实。

## 15. 面试追问与评分要点

### 面试追问

- 如何证明摘要没有丢失仍然有效的约束？
- 网页、Memory 和数据库互相冲突时，谁应该进入 Context？
- 探索性任务暂时没有直接目标进展，是否应该删除其上下文？
- Context Projection 由规则还是模型生成，如何验证它自身？

### 评分要点

优秀回答应区分 Event Log、Current State、Context Projection 和 Snapshot，提出来源、时效、安全、压缩不变量以及可执行的对照评测方法。
