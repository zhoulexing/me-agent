# 课题名称

## 1. 这个课题解决什么问题

用一句话说明它在 Agent 工程体系中承担的责任，以及它不负责什么。

## 2. 为什么会出现这个问题

说明缺少该机制时，Agent 会出现什么失败、风险或工程瓶颈。

## 3. 核心概念

定义关键术语，明确相似概念之间的区别。

## 4. 系统边界

说明它的输入、输出、上游、下游，以及与其他领域的边界。

## 5. 核心争议

把课题写成需要作出工程判断的问题，明确为什么不存在脱离场景的唯一答案。

## 6. 候选方案与决策维度

列出主要候选方案，并从确定性、副作用、上下文、状态、风险、成本、可恢复性和可评测性等维度比较。

## 7. 系统不变量

写清无论选择哪种实现都不能破坏的长期边界。

## 8. 工作机制

描述核心流程、状态变化和关键判断，不在这里陷入特定框架的实现细节。

## 9. 案例

每个课题至少包含一个案例或一段伪代码；工程机制类课题尽量同时包含两者。

### 场景

描述用户目标、初始状态、约束和环境。

### Harness 行为

描述 Harness 如何处理信息、控制执行或完成判断。

### 结果

说明真实结果和证据，而不只记录 Agent 的最终说法。

### 结论

指出案例证明了什么，以及不能推出什么。

## 10. 伪代码

伪代码至少表达输入、状态、判断、副作用和输出。必须明确标注为说明性伪代码，不能把设计设想写成现有项目已经实现的能力。

```python
def example(input_data, state):
    decision = decide(input_data, state)
    return decision
```

## 11. 失败案例或反例

描述缺少该机制、边界设置错误或异常路径没有处理时会发生什么。

## 12. 设计选择与权衡

记录主要方案、收益、代价和适用条件。

## 13. 主参考项目

只记录经过源码或官方文档核验的实现事实，主参考项目为：

- Claude Code
- Codex
- DeepSeek Harness

每项证据应包含文件、调用链或官方文档位置。尚未核验的内容标记为“待研究”，不能写成确认事实。

其他项目仅在能够提供独立、已经核验的实践价值时按需作为补充，不作为固定研究主线或固定模板章节。

## 14. 如何验证这套机制

说明测试方法、观察证据、评测案例和失败判定。

## 15. 面试追问与评分要点

给出能够区分概念记忆、工程经验和系统设计能力的追问，并说明优秀回答需要覆盖的关键判断。

## 16. 延伸问题

记录暂时没有答案、存在争议或需要进一步源码研究的问题。

## 17. 参考资料

优先记录一手来源、源码、官方文档和可以复现的实验。
