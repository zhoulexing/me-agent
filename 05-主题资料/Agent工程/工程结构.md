# Agent Harness 工程结构

目标是在 `projects/agent-harness/` 从零实现一套可运行、可验证、可用于讲解的 Agent Harness。下列三个包和目录是当前代码结构；后续能力按清晰的依赖边界增加。

## 目录

```text
projects/agent-harness/
├── apps/
│   └── cli/src/                # 命令入口与当前案例的依赖装配
├── packages/
│   ├── llm/src/
│   │   ├── contract/           # 统一消息、请求、流事件与错误
│   │   └── adapters/pi-ai/     # pi-ai 模型配置、输入输出转换与重放
│   ├── core/src/
│   │   ├── loop/               # 轮次、模型步骤和工具执行
│   │   └── tools/              # 工具注册与调用
│   └── session/src/
│       ├── events/             # 事件格式与校验
│       ├── projection/         # 从事件推导消息与轮次状态
│       ├── recovery/           # 中断修复
│       └── persistence/        # 存储契约与 JSONL 实现
├── examples/                   # 按学习阶段演进的可运行案例
├── tests/                      # 跨模块、CLI 与协议边界的测试
└── README.md                   # 运行方法与工程入口
```

借鉴 DeepSeek Harness 的通用模型契约、适配器、Agent Loop 和持久化边界；当前维持三个包，在包内按职责分文件。`llm` 不依赖 Core 或 Session，Session 只读取 LLM 契约，Core 使用两者，CLI 负责装配。后续增加模型适配器时只扩展 `llm/adapters/`；更换存储时实现 Session 的存储契约。

## 运行边界

```text
CLI 单次 / 交互 → CLI 装配 ─┐
                      ├─→ Agent Loop → 模型 / 工具 / 会话状态
CLI server → SDK Server┘
                 ↑
          JSON-RPC Protocol
```

- `apps/cli/` 负责命令解析、单次与交互输出、进程生命周期和当前案例的依赖装配。两种运行方式共用 `core/` 的 Agent Loop 和同一 Session；后续 `server --stdio` 也复用这条执行链。
- `core/loop/` 定义 Agent 的执行主干；ReAct 是步骤驱动的一种策略，不作为整个工程的顶层架构。
- 后续实现 JSON-RPC 时，可建立协议与 Server 模块，映射到同一 Agent Loop 和 Session，不持有另一套会话状态。
- Server 首先使用 stdio 上的逐行 JSON-RPC。标准输出只发送协议消息，诊断信息走标准错误。优先定义初始化、创建或恢复会话、开始或取消轮次、审批响应及进度事件；请求被接收与轮次完成分别表达。
- 后续加入 `context/`、`governance/`、`execution/` 等能力时，让它们分别负责上下文、权限和实际执行；`session/` 保留可恢复的事实。这些边界同时服务 CLI 与 Server。

## 从零到一的顺序

1. **最小闭环**：模型接口、Agent Loop、会话事件、一个受控工具和 CLI 单次运行。
2. **可靠运行**：权限与审批、取消、工具输出边界、会话持久化和恢复。
3. **对外接口**：JSON-RPC 协议与 stdio Server；用同一案例核对 CLI 和 Server 的行为。
4. **体系完善**：上下文压缩、更多工具和模型适配器、观测与评测；确有外部调用需求时增加 SDK Client。

每一步在 `examples/` 留下可运行案例，课程内容可据此解释问题、设计取舍、代码实现和验证结果。工程仓库的 README 记录实际运行方式；本主题目录继续保存原理研究与课程材料。
